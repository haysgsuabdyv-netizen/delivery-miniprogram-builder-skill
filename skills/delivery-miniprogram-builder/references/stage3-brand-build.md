# 阶段三：品牌模板匹配、搭建与交接

## 先把真实边界说清

内置模板库当前只有一个 `workbuddy-native-basic@1.0.0` 原生基础模板，加 `list-crud`、`form-result`、`profile` 三个页面骨架，**没有按品牌调性分类的现成模板**。所以「品牌模板匹配」不是从库里挑一个好看的主题，而是：用品牌资料定出可落地的 token，用标杆截图提取匹配特征，决定用哪个骨架（或自建页面），再把 token 落到 WXSS、图片与文案里。

交付说明里不要写「选用了某某品牌模板」——库里没有这个东西，写了就无法核对。写清「基于哪个骨架、替换了哪些点、品牌 token 落在哪些文件」才是可验收的说法。

## 1 · 品牌 token 表

只用附件 00 台账里状态为「已确认」的 `B-xx`。把品牌调性拆成能写进代码的项，每项带 `B-xx` 来源：

| 维度 | 要落到什么粒度 |
|---|---|
| 配色 | 主色/辅色/强调色/背景/文字色，全部 hex，注明使用场景 |
| 字体 | 字体名、字重、标题与正文字号、行高；无字体文件时标明系统字体回退 |
| 图片 | 来源（客户图片库 / 已接图片接口 `I-xx`）、构图与色调特征、裁切比例 |
| 文案语气 | 人称、句式长度、敬语习惯、禁用词、按钮动词风格 |

资料里没给、或状态为待确认/冲突的维度标「待补」。为了让工程能跑起来，可以给一个**显著标注的临时值**（例如 `临时值-待替换`），但必须同时写进附件 04 章节的验收清单，注明「客户确认后替换」。不要用「行业通用蓝」「简约现代」这类没有出处的默认值冒充品牌结论，这正是「通用模板感」的来源。主文件判「暂缓」时，本章节标注「未启动：待补齐」，不产出 `T-xx` / `BT-xx`。

```markdown
| ID | 维度 | 值 | 依据 | 落地位置 | 状态 |
|---|---|---|---|---|---|
| BT-01 | 主色 | #XXXXXX | [B-01] | app.wxss / 变量 | 已确认 |
| BT-02 | 正文字体 | 待补，临时用系统字体 | [B-03] | app.wxss | 临时值-待替换 |
```

## 2 · 标杆截图只用于匹配

参考案例 / 标杆截图在台账里已登记为 `B-xx` 并标注「仅用于模板匹配」。允许提取的是**特征**：布局密度、信息层级、留白节奏、圆角与描边气质、图文比例、交互动效强度。不允许搬运其中的图文、版式结构、图标与文案——既会造成品牌不一致，也有版权风险。

匹配结论写成可核对的一句话：截图特征 → 本项目的对应做法 → 依据哪个 `B-xx`。

## 3 · 模板决策 T-xx

输入是第 2 段的 `P-xx` 页面形态 + 上一步的匹配特征 + 内置骨架选择表：

| 页面形态 | 可用骨架 |
|---|---|
| 一组条目，可增删改（列表、记录、打卡） | `list-crud` |
| 填信息提交后给结果（预约、报名、登记） | `form-result` |
| 头像昵称加功能入口列表（我的、设置、关于） | `profile` |
| 以上都不匹配 | 不套骨架，按原生工程约束增量实现 |

每个 `T-xx` 写明：对应页面 `P-xx`、选了哪个骨架或自建、依据、以及要替换的点（字段、文案、storageKey、标题、状态）。骨架只是起点，可以整体采用、部分采用或不采用；采用骨架不等于品牌已经落地，token 仍要逐项写进样式与文案。

## 4 · 品牌落地清单

对每个 `BT-xx` 给出实际落点：哪个文件、哪一段 WXSS、哪个页面文案、哪处图片调用。第 2 段的合规落点 `C-xx` 也要在这里复核一遍（例如资质展示位、禁用表述、隐私字段是否出现在页面上）。

## 5 · 交接给内置能力

把前三段整理成「搭建输入规格」，交给 `mini-program-development` 执行。规格至少包含：

- 项目目录与是新工程还是已有工程
- 页面清单 `P-xx` 与每个页面的关键状态（loading / empty / error）
- 模块 `M-xx`、数据实体 `D-xx`、接口 `I-xx`（含鉴权、返回字段、失败态）
- 存储决策（本地 / 云端）与理由
- 品牌 token 表 `BT-xx` 与落点
- 模板决策 `T-xx`（骨架或自建）
- 合规落点 `C-xx`
- 待联调项与验收点

下游按内置流程走：新建工程用 `workbuddy_miniprogram_scaffold` 展开基础模板，已有工程只做增量修改；需要数据、登录、文件或 LLM 时加载 `cloud-service`；完成后预览、原生校验、按需用 `sites` 生成应用卡。本 Skill **不**手写 `project.config.json`、`app.json` 等基础文件，**不**另造预览与发布链。

把内置能力回报的实际结果记进附件 04 章节：跑了什么校验、结果如何、哪些没跑。预览成功不等于原生编译或发布成功，没执行的不要写「通过」。

## 6 · 附件 04 章节：交付说明与验收清单

```markdown
# 04 交付说明与验收清单

## 做了什么 / 放在哪
（两份交付文档、三段成果、工程目录、应用卡）

## 实际执行的校验
（逐项写：执行了什么、结果；未执行的明确列为未执行）

## 待补资料与待联调
（与主文件的返工风险清单一致，含临时值待替换项）

## 验收清单

| 标准 | 结论 | 证据 / 待办 |
|---|---|---|
| 判断有依据：每条 V/F/X 可追溯、无臆造、无漏项 | 通过 / 未通过 / 待客户确认 | 覆盖矩阵 + check_delivery.py 结果 |
| 架构来自资料：换资料会变、无固定四模块 | | 链路表 + P-xx 派生依据 |
| 品牌一致：配色字体图片语气有来源、工程已落地 | | BT-xx 落点清单 |
| 可串联可验收：编号链闭合、能跑通能联调 | | 脚本结果 + 预览与校验记录 |
| 资料不全仍能开工判断：待补清单含责任人与补齐标准 | | 主文件返工风险清单 |
| 冲突不静默择一：并列各方原文与出处 | | 主文件冲突表 |
```

## 进入验收前的自检

- 每个 `BT-xx` 都有状态为「已确认」的 `B-xx` 来源，或明确标为临时值并进了验收清单
- 标杆截图只出现在「特征匹配」里，没有图文被搬进页面
- 附件 03 章节写明了下游是 `mini-program-development`，且没有手写基础工程文件
- 附件 04 章节「实际执行的校验」与真实执行情况一致，没有把未跑的写成通过
- 主文件判「暂缓」时，附件 01–04 没有为凑链路编造编号
- 运行 `python scripts/check_delivery.py <交付目录>` 通过，并把 `--json` 原始输出留成 `verification.json`
