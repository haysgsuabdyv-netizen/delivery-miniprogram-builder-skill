# 入口边界、事实分块与待补清单

## 为什么不再要求「资料齐了才启动」

原来的四条硬条件（需求已确认、原型评审通过、品牌资料齐全等）把本 Skill 的位置放在了最难的活之后：等别人把需求谈清、原型定稿、VI 交齐，剩下能做的就只是把已有内容重排一遍。而真实项目里，开工时手上往往只有合同、几段聊天记录、一份会议纪要和几张原型截图，还常常前后对不上。**资料不全不是异常，是这项能力最该发挥作用的时刻。**

入口放宽的依据标准没有放宽：能进三段推导的仍然只有「已确认」的事实。变化只在于，缺的、含糊的、互相矛盾的部分，现在会被明确列出来并写清怎么补，而不是让整个任务停在门口。

## 两条边界（只判这两条）

| 边界 | 怎么判定 | 常见误判 |
|---|---|---|
| 处于签约后交付语境 | 任务写明「合同已签 / 交付任务已下达 / 进入开工 / 实施排期」，或提供了合同、交付单、立项结论 | 把「客户很感兴趣」「准备报价」当成已签 |
| 至少有一份来自该客户的真实资料 | 合同、聊天记录、会议纪要、访谈纪要、原型截图、旧系统说明、需求文档、VI 任意一种 | 把「行业 = 医美」「做个餐饮小程序」当成客户资料 |

资料齐全程度不参与判定。合同签了但只有一张原型截图，照样启动；反过来，资料堆得很齐但明确是售前演示，仍然不启动。

**不满足时怎么回应**：说明这两条边界里哪条不满足，指出补齐路径（找客户要一份真实资料，或确认已签约/已下达交付任务），并点名改用 WorkBuddy 内置的 `mini-program-development` 做工程化搭建。不产出功能清单、不产出架构、不产出小程序。只写「当前不适用」而不给可执行落点，交付同学还得再问一次。

## 资料台账：登记状态，不筛选资料

附件 `00` 章节是整条链路的锚。每份收到的资料一个编号，锚点要能让人翻回原文；状态一栏写「已确认 / 待确认 / 前后冲突」。没收到的资料不编号，进主文件的待补清单。

```markdown
# 00 资料台账

- 客户 / 项目：（真实名称）
- 合同签订状态：（已签 / 交付任务已下达，写明依据）
- 开工结论引用：（主文件里的结论编号）
- 交付日期：（今天）

## 需求侧 R

| ID | 文件 / 来源 | 锚点 | 内容摘要（原文摘录） | 状态 |
|---|---|---|---|---|
| R-01 | 会议纪要 11-03 | §2 范围 | 「一期做预约，商城二期」 | 前后冲突 |
| R-02 | 需求文档 v2.3 | §4 场景 | | 已确认 |

## 品牌侧 B

| ID | 文件 / 来源 | 锚点 | 内容摘要 | 状态 |
|---|---|---|---|---|
| B-01 | VI 手册 | 色彩章节 | | 已确认 |
| B-02 | 客户微信 11-05 | 「颜色你们先看着来」 | 口头、无确定值 | 待确认 |

## 合规侧 C

| ID | 文件 / 来源 | 锚点 | 约束内容 | 强度 |
|---|---|---|---|---|
| C-01 | 客户合规清单 | 第 1 条 | | 硬约束 |

## 环境侧 E

| ID | 来源 | 内容 | 状态 |
|---|---|---|---|
| E-01 | 客户提供的图片接口 | 接口地址、鉴权方式、返回字段 | 已接好 |
```

要点：

- 「内容摘要」摘录不推断。资料里没写的写「未提及」，不替客户补全。
- 参考案例 / 标杆截图登记为 `B-xx` 并标注「仅用于模板匹配」，从一开始就防止被当成需求来源或直接搬运。
- `E-xx` 登记接口时写清鉴权与返回字段，第 2 段的接口设计才有依据。
- 合规约束客户没提供时，把「合规要求未明确」列为待补项并在验收清单标风险；医疗、金融、教育等受监管行业不自行编写行业法规条款。

## 把客户沟通切成事实块

按「一件事一块」切，不要把整段会议纪要当成一个事实。每块记录：这件事是什么、来自哪份资料的哪个锚点、原文怎么说、状态。状态定义：

| 状态 | 判定 | 允许的去向 |
|---|---|---|
| 已确认 | 有明确出处，且没有其他资料给出相反说法 | 作为 `F-xx` / `P-xx` / `BT-xx` 的依据 |
| 待确认 | 只有口头、单句、截图里看不出结论，或资料未提及 | 主文件待补清单，不写成结论 |
| 前后冲突 | 两份及以上资料对同一件事说法不一致 | 主文件冲突表，并列各方原文 |

不能升级为「已确认」的内容：客户口头说过、销售话术、售前承诺、「行业通常都有」、截图里推测出来的交互、只有标题没有内容的章节。这些东西写进文档时，要连状态一起写，别让下一手读的人以为已经定了。

## 冲突并列，不静默择一

同一件事出现两个版本时，在主文件里并排放出两条原文与出处，不替客户挑一个、不按「哪份文件更新」自行裁定：

```markdown
## 前后冲突

| 冲突项 | 版本 A（原文 + 出处） | 版本 B（原文 + 出处） | 需谁裁定 | 裁定到什么程度才能继续 |
|---|---|---|---|---|
| 一期范围 | 「含商城与在线支付」— 合同 §3 | 「一期只做预约，商城二期」— 会议纪要 11-03 §2 | 客户决策人 + 我方 PM | 书面确认一期范围并双方签字 |
```

冲突没有裁定前，依赖它的功能、页面、接口一律标「待补」，不进入 `F-xx` 推导。把冲突悄悄抹平成一句「一期做预约和商城」，正是返工的起点。

## 返工风险清单（主文件的核心）

只列「现在没说清、以后一定会返工」的问题，不列锦上添花的优化项。每条写全五项：

```markdown
| 缺口 / 含糊点 | 谁来补 | 补到什么程度才能继续 | 不补的后果 | 影响哪一段 |
|---|---|---|---|---|
| 品牌主色与字体未定 | 客户品牌负责人 | 提供 VI 色值 + 字体文件与字号规范 | UI 整体返工，验收被退回 | 第 3 段 |
| 会员积分规则未说清 | 客户业务方 | 书面给出获取/兑换/过期规则 | 数据结构与接口重写 | 第 1、2 段 |
| 图片接口鉴权未提供 | 我方 PM 对接客户技术 | 给出鉴权方式与返回字段样例 | 图片模块无法联调 | 第 2、3 段 |
```

- 「谁来补」写具体角色，不写「相关方」。
- 「补到什么程度」写可验收的交付物（书面确认、色值与字体文件、接口字段样例），不写「进一步沟通」「尽快确认」。
- 「不补的后果」写具体到哪一段返工，方便项目负责人排优先级。
- 缺口按「阻断 / 影响质量 / 可后置」分组，一次问清，不要每读一份资料就问一次。

## 开工结论

主文件最后给一个明确结论，并指回事实分块与返工风险清单的编号：

- **继续**：关键已确认事实足够覆盖本次范围，三段照常推导。
- **暂缓**：存在阻断级缺口或未经裁定的冲突。附件只写 00 台账与待补清单，01–04 标注「未启动：待补齐」，不编造 `F-xx` / `P-xx` / `BT-xx`。
- **部分继续**：写明哪些段可以基于已确认事实先做、哪些必须等补齐；已做部分不得依赖待确认或冲突的事实块。

结论不为「有产出」而写「继续」。资料只有几张截图时，一份说清「缺什么、谁补、补到什么程度」的主文件，比一套看起来完整却靠猜的架构有用得多。

## 证据索引

主文件为每条结论留一条可回查的记录：结论 → 资料文件名 → 锚点（章节 / 时间 / 条目）→ 原文摘录。没有原文可引的，明确写「无资料依据，列为待补」，不要写「已核对」。

## 进入第 1 段前的自检

- 两条边界都有明确依据，没有靠推测通过
- 台账里每个编号都有文件名、锚点与状态
- 待确认与冲突的事实块都没有被写成结论
- 冲突项并列保留了各方原文，没有静默择一
- 返工风险清单每条都写了谁来补、补到什么程度、不补的后果
- 开工结论与事实分块状态一致；暂缓时附件没有凑出编号链
- 参考截图已标注「仅用于模板匹配」
