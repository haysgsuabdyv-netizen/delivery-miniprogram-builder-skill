# 阶段一：价值与功能判断

## 为什么这一段先做

交付阶段最贵的返工，是做了客户没确认的功能、漏了客户确认过的功能。把「该做什么」先收敛成一张带出处的清单，后面的架构、模板、代码才有唯一依据。这一段不是写方案亮点，是给后面每一段发编号。

## 输入

只用附件 `00 资料台账` 章节里**状态为「已确认」**的 `R-xx`（需求/目标用户/核心场景/已确认原型）、`C-xx`（合规硬约束）、`E-xx`（已接接口）。`B-xx` 品牌资料留到第 3 段，`E-xx` 中的接口能力可以作为可行性约束，但不能反过来变成需求。

状态为「待确认」或「前后冲突」的事实块不参与本段：它们留在主文件的返工风险清单里，等补齐或裁定后再进入推导。主文件开工结论为「暂缓」时，本章节只标注「未启动：待补齐」，不凑 `F-xx` / `V-xx` / `X-xx`。

## 方法

1. **逐条走查**：对每个状态为「已确认」的 `R-xx`，抽出「客户目标 / 目标用户 / 使用频次与场景 / 原型页面 / 明确写入的排除项」。抽不出来的写「未提及」，不补写。
2. **定价值点 `V-xx`**：一条价值点 = 客户能获得的具体改变 + 来自哪条需求 + 怎么验证它发生了。避免「提升品牌形象」这类无法核对的表述；如果资料里本身就是这么写的，照录并标注「客户原文，未给验证口径」。
3. **定该做功能 `F-xx`**：把已确认原型里的每个页面与交互，映射成功能条目。原型里没有的，除非需求文档明确写了，否则不新增。
4. **定不做/后置 `X-xx`**：三类来源——需求文档明确排除的、原型评审砍掉的、本次范围外但容易被顺手加上的（例如「电商通常都有购物车」）。每条写清「为什么不做」与依据；没有依据就不写这一条，别为了显得周全编一堆排除项。
5. **排优先级**：P0 = 已确认原型覆盖且核心场景必需，或合规硬约束要求；P1 = 已确认但可二期；P2 = 资料里只是提及、未确认。优先级理由必须引用状态为「已确认」的 `R-xx` 或 `C-xx`，不按个人经验排。
6. **覆盖矩阵**：左列是台账里所有「已确认需求 / 原型页面」，右列是对应的 `F-xx` 或 `X-xx`。逐行闭合，不允许空行；台账里没有对应结论的，回头补全或登记为待补。
7. **状态核对**：下笔前确认所引 `R-xx` 的状态是「已确认」。引用了待确认或冲突条目，结论退回重写。

## 越界检查

如果出现下面任何一种，说明这一段已经开始臆造，退回重做：

- 用「行业通常都有」作为新增功能的理由
- 把标杆截图里的功能当成客户已确认需求
- 把售前口头承诺、销售话术当成需求依据
- **把状态为「待确认」或「前后冲突」的事实块当成已确认需求，或据此写出 `F-xx` / `X-xx`**
- 价值点没有任何 `R-xx` / `C-xx` 引用
- 覆盖矩阵里有需求没有对应结论，或有结论找不到需求
- 为了凑数把同一条需求拆成多个价值点，或凭空加「提升转化」「增强粘性」这类无出处表述
- 资料严重不全、主文件已判「暂缓」，却仍写出一整套功能清单

## 交给第 2 段的东西

只有 `F-xx`（带优先级）与 `X-xx`（防止架构阶段把排除项又做回来）、`C-xx`（硬约束）。`V-xx` 留在交付说明里向客户解释「为什么做这个」，不参与架构推导。
