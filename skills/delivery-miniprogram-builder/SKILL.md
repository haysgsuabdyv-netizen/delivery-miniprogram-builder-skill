# 签约后交付：开工判断与可核对的搭建规格

## 这个 Skill 解决什么

交付阶段最贵的返工，往往不是代码写错，而是开工时没人发现「客户其实没说清」。资料不齐、聊天记录和合同对不上、原型只有几张截图、品牌 VI 还没发——这是常态，不是异常。等到架构和页面做完才发现，返工成本已经付掉了。

本 Skill 的价值前移到项目开工：**有什么资料先给什么，把其中确定与不确定的部分分清楚，列出会导致返工的缺口，说明谁来补、补到什么程度才能继续**。资料齐全时，它继续把已确认的事实逐段转成可上线的搭建规格。

资料不全不等于不能开工，也不等于可以靠猜开工。结论只有两种：能继续的部分按已确认事实推导，不能继续的部分明确暂缓并写清补齐条件。任何情况下都不把「客户大概是这样」写成事实。

## 入口：有什么资料先给什么

先判适用边界，再登记资料状态。判定细节见 [入口边界、事实分块与待补清单](references/intake-and-gate.md)。

| 边界 | 判定依据 | 不满足时 |
|---|---|---|
| 处于签约后交付语境 | 合同已签、交付任务已下达，或任务明确说进入开工／实施 | 售前演示、只给行业名、没有任何该客户资料 → 不启动本 Skill，改用内置 `mini-program-development` |
| 至少有一份来自该客户的真实资料 | 合同、聊天记录、会议纪要、原型截图、旧系统说明任意一种即可 | 同上 |

**资料齐全与否不是启动条件，而是输入状态。** 不再要求需求文档、已确认原型、品牌资料三者齐备；不因为缺资料而停止，也不要求补齐后再来一次。凡是收到的资料，逐份登记进附件 00 台账并标注状态；没收到的，写进主文件的待补清单。

这道边界只区分「是不是这个客户、是不是交付」，不区分「资料够不够」。把资料齐全当门槛，等于把最难的活预设成别人已经做完，本 Skill 就只剩把已有内容重新整理一遍。

## 事实分块与确定程度

客户沟通里的事实要切成独立小块，逐块标注来源与状态，别把模棱两可的内容包装成事实：

| 状态 | 含义 | 能用来做什么 |
|---|---|---|
| 已确认 | 有明确出处且无相反说法（合同条款、评审结论、书面确认的需求） | 可以作为 `F-xx` 功能、`P-xx` 页面、`BT-xx` 品牌 token 的依据 |
| 待确认 | 只有口头、单句、截图里看不出结论，或资料未提及 | 只能进主文件待补清单，不得写成结论 |
| 前后冲突 | 两份及以上资料对同一件事说法不一致 | 并列保留各方原文与出处，不静默择一；由客户或项目负责人裁定后才能升级为已确认 |

摘录不推断。资料里没写的写「未提及」；同一件事有冲突时，在台账和主文件里把两条原文并排写出，注明各自的文件名与锚点。**「客户口头说过」「行业通常这样」「销售当时提了一句」都不算已确认。**

只有状态为「已确认」的事实块能进入三段推导。这条约束是「判断有依据」在新入口下仍然成立的原因：入口放宽了，依据标准没有放宽。

## 主文件：开工判断与决策清单

主文件是给项目负责人做决定的，不写方案亮点，只写四件事：

1. **资料盘点**：收到了什么、每份的状态、覆盖了哪些维度。
2. **事实分块表**：已确认／待确认／前后冲突三块，每条带文件名与锚点；冲突项并列原文。
3. **返工风险清单**：现在没说清、以后一定会返工的问题，逐条写明「谁来补 → 补到什么程度才能继续 → 不补的后果 → 影响哪一段」。「谁来补」写具体角色（客户品牌负责人、客户业务方、我方 PM、客户决策人），「补到什么程度」写可验收的交付物（例如「书面确认一期范围并签字」「给出 VI 色值与字体文件」），不写「进一步沟通」这类无法验收的话。
4. **开工结论**：继续／暂缓／部分继续。部分继续时，明确哪些段可以基于已确认事实先做、哪些必须等补齐。结论要能追溯到事实分块表里的编号。

每条结论附带证据索引：指向资料的文件名、章节／时间／条目与原文摘录。证据索引就是「实际验证证据」的内容部分，不另写一份空泛的「已核对」声明。

## 与内置能力的分工

| 阶段 | 由谁负责 |
|---|---|
| 签约前、无客户资料的行业演示 | 不在本 Skill 范围，交给 WorkBuddy 内置能力 |
| 签约后：资料盘点、事实分块、开工判断、价值与功能判断、架构、品牌匹配、搭建规格 | 本 Skill（上游） |
| 原生工程展开、页面实现、云服务接入、编译预览、发布 | 内置 `mini-program-development`（下游），本 Skill 只交接规格，不复写工程 |

在可读取资料及写入文件的 Agent Skills 客户端中生成交付规格。当前环境可调用 `mini-program-development` 时将规格交给它。缺少该能力时，交付搭建输入规格，并在附件 04 记录待搭建、待预览和待联调的项目。

**事实边界，别写错**：内置的 `mini-program-development` 是通用开发闭环能力，本身没有「只做售前演示」的定位，也没有「只输入行业就出对标 Demo」的功能。本 Skill 的适用范围由上面的入口边界保证，不是靠假设内置能力只覆盖签约前。交付说明里不要出现「内置能力负责售前 Demo」这类未经核实的表述。

已核实的下游真实资产：

- `workbuddy_miniprogram_scaffold` 展开 `workbuddy-native-basic@1.0.0` 原生基础模板
- 页面骨架三个：`list-crud`、`form-result`、`profile`（见内置 `references/skeletons.md`；无匹配时直接增量实现）
- 需要数据、登录、文件或 LLM 时由内置能力加载 `cloud-service`；发布走 `sites`
- 当前模板库**没有**按品牌调性分类的现成模板；品牌差异通过增量 WXSS、图片与文案实现，见 [阶段三](references/stage3-brand-build.md)

## 三段递进与核对链

附件里用编号把五段成果串起来，任何一条结论都能顺着编号往回查、往下追：

| 附件章节 | 定义的编号 | 必须引用 |
|---|---|---|
| 00 资料台账 | `R-xx` 需求 / `B-xx` 品牌 / `C-xx` 合规 / `E-xx` 环境 | 原始文件与锚点、状态 |
| 01 价值与功能判断 | `V-xx` 价值点 / `F-xx` 该做功能 / `X-xx` 不做或后置 | 状态为「已确认」的 `R-xx`、`C-xx` |
| 02 架构设计 | `P-xx` 页面 / `M-xx` 模块 / `D-xx` 数据 / `I-xx` 接口 | `F-xx`、`E-xx` |
| 03 品牌与搭建 | `T-xx` 模板决策 / `BT-xx` 品牌落地项 | `B-xx`、`P-xx` |
| 04 交付说明与验收 | 验收项 | 前三段全部编号 |

编号用两位数字（`R-01`）。引用写成方括号内联，例如 `[R-03]`、`[F-02]`；一个结论有多个依据就并列多个方括号。这一步看着机械，但它是「判断有依据、架构来自资料、逐段可核对」唯一能被机器检查的实现方式。

### 为什么坚持固定文件名和编号

对比评测里有个值得记住的现象：不给这套约定时，模型通常也能写出像样的价值判断和架构，也会主动拒绝售前 Demo，内容判断的差距并不大；但每次会换一套文件名、自创一套编号、验收清单换个说法，结果是验收方只能靠人读，既没法自动查漏项，也没法把「价值判断 → 架构 → 模板 → 代码」串成一条链。差距几乎全部落在「可核对、可验收」上。

所以这套约定是交付契约，不是格式偏好：验收方拿着附件 04 的清单，能顺着 `F-02 → P-02 → BT-03` 一路翻回 `R-03` 与 `B-01`；`check_delivery.py` 能把「有没有依据」从一句主观承诺变成可运行的检查。不要为了「写得更自由」换掉两份文件名、省略方括号引用，或改用自定义编号体系。原五份文档的内容与编号链完整保留在附件章节里，只是不再要求拆成五个文件。

**暂缓时不要凑链**：主文件结论为「暂缓」时，附件只写 00 台账与待补清单，01–04 标注「未启动：待补齐」，不要为了通过校验而编出 `F-xx`／`P-xx`／`BT-xx`。脚本对暂缓场景改用另一组检查。

## 交付目录

在一个交付目录下产出，目录名由交付同学指定或默认 `delivery-<客户简称>/`：

```
<交付目录>/
├── 00-开工判断与决策清单.md   # 主文件：项目负责人决策用
├── 01-开发接手包.md           # 附件：开发直接接手，内含 00–04 五个章节
├── verification.json          # 实际验证证据：check_delivery.py --json 的原始输出
└── miniprogram/               # 由内置能力生成的工程，本 Skill 不手工重造
```

**交付文档只有两份**。`verification.json` 是脚本运行的留痕，不是第三份文档；每条结论指向哪份资料的哪一段，写在主文件的证据索引里。格式骨架见 [assets/delivery-record.md](assets/delivery-record.md)，占位内容必须换成真实资料。

## 执行

默认连续跑完并逐段留痕；只在需要客户裁定冲突、或补齐条件会改变开工结论时，把问题合并成一份清单再问一次，不要每段都停下来等签字。

### 第 0 步 · 入口判断、事实分块与开工结论

按 [入口边界、事实分块与待补清单](references/intake-and-gate.md) 核对两条边界，把每份资料登记成 `R/B/C/E` 条目，写清文件名、锚点和状态。把客户沟通切成事实块并分三态，冲突项并列原文。产出主文件：返工风险清单（谁来补、补到什么程度、不补的后果）、证据索引、继续／暂缓／部分继续结论。

### 第 1 段 · 价值与功能判断（附件 01 章节）

按 [阶段一](references/stage1-value-scope.md) 从台账里状态为「已确认」的事实逐条走查，产出价值点、该做与不做／后置的功能清单（含优先级与理由）、需求覆盖矩阵。每条结论带来源编号；待确认与冲突的事实块不得作为依据。

### 第 2 段 · 架构设计（附件 02 章节）

按 [阶段二](references/stage2-architecture.md) 以 `F-xx` 为唯一输入推导页面、模块、数据与接口，产出「功能 → 页面 → 模块 → 数据/接口」链路表。每个页面写明派生自哪个功能、为什么需要这一页。顺带定下本地存储还是云端保存。

### 第 3 段 · 品牌模板匹配与搭建（附件 03 章节）

按 [阶段三](references/stage3-brand-build.md) 把品牌调性拆成可落地的 token 表，用标杆截图做模板特征匹配（只提特征，不搬内容），形成模板决策 `T-xx`。把架构与品牌 token 整理成「搭建输入规格」，调用内置 `mini-program-development` 落地工程，并把它回报的预览与校验结果如实记入附件 04。品牌维度待补时给显著标注的临时值并列入验收清单，不用「行业通用色」冒充。

### 第 4 步 · 交付说明与验收清单（附件 04 章节）

写清做了什么、放在哪、跑了哪些校验、哪些没跑、还有哪些待补资料与待联调接口。验收清单按下面六条标准逐项给「通过 / 未通过 / 待客户确认」，不要笼统写「已完成」。

### 第 5 步 · 运行校验并留痕

```bash
python scripts/check_delivery.py <交付目录> --json > <交付目录>/verification.json
python scripts/check_delivery.py <交付目录>
```

把 `--json` 的原始输出存成 `verification.json`，作为「实际验证证据」的运行部分；不要事后改写或美化脚本结论。脚本检查两份文件是否齐备、事实分块与待补清单是否合格、编号是否定义过、引用是否可解析、功能结论是否有已确认依据、页面是否追得到功能、品牌落地项是否有来源、是否声明下游交接，以及验收清单是否完整。它检查的是链路闭合，不替代人工判断内容好坏；报 PASS 后仍要人工读一遍结论。

## 验收标准

1. **判断有依据**：每条 `V/F/X` 都能追到状态为「已确认」的资料，不臆造需求、不漏已确认需求；覆盖矩阵无空行。
2. **架构来自资料**：换一份客户资料会产出不同架构，而不是换行业只换文案；不套固定四模块；无与任何 `F-xx` 无关的页面。
3. **品牌一致**：配色、字体、图片、文案语气都有 `B-xx` 来源或明确标注待补；标杆截图仅用于匹配，不直接搬运。
4. **可串联、可验收**：附件 `00 → 01 → 02 → 03 → 04` 编号链闭合，脚本通过；成果能跑通、能联调，未验证项如实列出。
5. **资料不全仍能开工判断**：只有零散资料时照常产出主文件；待补清单覆盖关键缺项，且每条写明谁来补、补到什么程度才能继续、不补的后果。
6. **冲突不静默择一**：前后矛盾的资料被识别并单列，并列各方原文与出处，不包装成已确认事实，不替客户选一个版本。

## 边界与禁止项

- 只在签约后交付阶段启用；售前演示、只给行业名的对标 Demo 一律拒绝。
- 不以「行业特定 Prompt」当主输入；行业只是资料的一个属性，不是需求来源。
- 不把「待确认」「前后冲突」的事实写成已确认结论，不把「待补」写成看起来确定的值。
- 不因资料不齐而拒绝启动，也不为了凑齐编号链而编造功能、页面或品牌结论。
- 不套用固定四模块骨架，不预设页面数量。
- 标杆截图只用于提取布局密度、信息层级、交互气质等特征，不搬运其中图文、版式与文案。
- 不重造原生工程：不手写 `project.config.json`、`app.json` 基础文件，不另造预览与发布链。
- 不声称执行过没有实际执行的编译、真机预览、联调或验收。
- 不写「内置能力负责售前 Demo」这类未经核实的表述。
